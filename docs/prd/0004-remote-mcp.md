# Authenticated remote Wallit MCP

Expose every existing end-user Wallit capability through a remote Streamable HTTP MCP endpoint hosted by the production app on Railway, independently of any Mac process. Scope "everything" to the authenticated account's current permissions and explicitly consented Spaces and OAuth scopes. Never expose arbitrary SQL, other users' accounts, or secrets.

Use OAuth authorization code + PKCE S256 with protected-resource metadata and authorization-server discovery, public client DCR, explicit browser consent, exact registered redirects, audience binding, short-lived access tokens, rotating refresh tokens, reuse detection and family revocation. Existing Wallit browser authentication identifies the consenting user. New grants and credential persistence require that user's explicit in-flow confirmation. All protected MCP methods return 401 anonymously and 403 for insufficient scope.

Reuse existing domain operations and service rules. New movements created by any MCP call must always have `needsReview=true` at commit, including both transfer legs, bulk, splits, imported movements and settlement/payment workflows. Clients cannot supply an override. Review is a separate explicit operation. Ordinary edits must preserve pending review. Mutations must be transactional, audited, validated, retry-safe and concurrency-safe.

Cover account settings, Spaces and memberships, categories, accounts and currencies/opening balances/credit limits, investments, CLP/USD income and expenses, transfers (including the existing limited send to a shared-Space member’s unassigned pending inbox, without private financial access), receivables and settlements, emergencies, loans, reports, imports and review. Maintain an explicit parity inventory. Do not invent tags, budgets, installments, recurrent scheduling, password/profile edits or bank-browser automation where Wallit's app has no such capability.

Tests must exercise real route transport, discovery and OAuth, successful reads and writes, every catalog entry, invalid inputs, cross-user and Space isolation, revocation/expiry, idempotency and concurrent writes, transactional rollback, and review policy, using a disposable local PostgreSQL fixture. Keep the existing cron unchanged. Perform independent Standards and Spec/security reviews, publish a draft PR, validate final CI before merge, verify the exact production commit and SUCCESS deployment. Production writes are restricted to an explicitly approved isolated fixture; authenticated production read and plugin OAuth validation await user's connection consent.

Deliver endpoint/discovery/scopes and a portable plugin configuration. The parent handles cloud plugin registration and interactive authentication. A local-only MCP config does not fulfill the cloud plugin requirement. Do not claim full completion until production and installed plugin authentication are verified, or report the exact remaining blocker.
