# Bank email cron audit, 2026-10-03

## Scope and base

Implementation base: `60647e3cddab49e4082de01d2a8305954c9915bc`, current `master` at the start of work. Railway cron source is `rmena1/wallit`, branch `master`, root `workers/bank-email-cron`, 10-minute schedule. The effective restart policy was `NEVER`.

No production credentials were read. No test contacted production HTTP/IMAP/database endpoints or wrote Wallit entries. No replay/backfill/manual import or cursor reset was performed. Private Gmail content is not present in this commit or report.

## Repaired findings

1. Substring sender allowlisting could trust a display-name/suffix spoof. Exact mailbox matching plus the topmost trusted Gmail DMARC result now governs accepted senders, including forwarding with SPF for gmail.com.
2. Premature process exits bypassed cleanup and reported success for blocked mail. An effect-injected runner now returns exit 1 for blocked/errors and releases/closes on every path.
3. Pooled advisory locks could land on different sessions. Lock, cursor and audit queries now share a reserved session with bounded SQL statement and client transport time, sticky invalidation on disconnect, and backend PID/advisory ownership checks before effects and every import retry. The tracked physical socket is destroyed on a transport deadline without relaxing TLS policy.
4. UIDVALIDITY reset and folder overwrite risked replaying historical user-deleted imports. Both now fail closed without cursor mutation/reset; cursor updates are monotone and verified.
5. Whole-inbox sender search and unlimited fetching lacked bounds. Search now includes UID, sorted batches are bounded, messages have byte limits, and incomplete/duplicate fetch results fail the whole batch.
6. IMAP operation disconnects could leave requests pending. Open/search/fetch now handle error/end/close and bounded deadlines, while preserving read-only/PEEK semantics.
7. MIME parse failures were omitted while later UIDs could advance. Failed messages remain explicit blocking records. Empty plain text in multipart mixed messages now falls back to decoded HTML; UTF-8 chunks are assembled as bytes.
8. Real layouts exposed BCI international line breaks, Tenpo incoming bank transfer/peer payment/credit repayment, and MercadoPago named-card/repeated-merchant boundaries. Synthetic regressions cover the repairs.
9. MercadoPago receipt sender was incorrectly used as the funded ledger for a BCI card. Known explicit funding routes to the known BCI card; unknown cards and contradictory routing are blocked.
10. Calendar-invalid dates, invalid clock values, unsafe/zero money, absent identity and malformed classifier choices could reach unsafe disposition. Validation is fail closed, header-only proxies use Chile local time, and FX must be configured explicitly.
11. Import requests had no deadline, incomplete HTTP retry coverage and could expose remote error bodies. Request+body decoding are bounded, retries retain identical source identity/payload, and new logs use fixed reasons without remote bodies/credentials.
12. New processing logs no longer store subjects or full sender/Message-ID. Existing rows remain untouched.
13. Independent review caught unverified brand/last4 funding, unresolved own-card repayment conversion to expense, and incomplete successful incoming receipt skips. These now retain the UID rather than infer a ledger or consumption event.
14. Work budget is propagated to IMAP/classifier/import operations and retries. No new import starts after that deadline. Confirmed-disposition logging/cursor and bounded transport cleanup can extend beyond the work budget; the budget is not a claim of exactly eight minutes wall-clock total.
15. Original date-header components are validated before Date normalization; malformed February/clock values cannot silently become a March transaction.

## Validation

- Genuine corpus: exactly **100** unmodified messages read via authorized Gmail connectors, with **100 distinct account+Gmail IDs and 100 distinct RFC Message-IDs**
- Providers: **35 BCI, 41 Tenpo, 24 MercadoPago**
- Classification ground truth was independently prepared from the source messages, without running the application parser
- MIME: all 100 include HTML; 41 include plain text, 18 multipart mixed, 3 PDF attachments
- Authentication: 100 trusted topmost mx.google.com results with aligned DMARC pass
- Event ground truth: 93 completed notices, 3 statements/nontransactions, 4 failed payments
- Currency evidence: 90 CLP, 7 USD, 3 statement records without a single transaction currency. ISO CLP units were explicitly converted to Wallit's centavos contract rather than silently altering source truth
- Isolated final expectation pass: **100/100**; **87 local mock import routes**, **6 deliberate fail-closed routing cases**, **7 rejected/nontransaction cases**. This does not mean 100 production imports
- Checks include sender/auth, amount/currency/date/time/type, merchant where specified, account routing, credit repayments as transfers, invalid/ambiguous non-import safety, and raw SHA-256 integrity
- Committed synthetic suite: **202/202** passing at the candidate checkpoint; includes transport-denial proof against HTTP/TLS/IMAP/PostgreSQL and deadline/partial-failure regressions
- Syntax checks and `git diff --check` passed. Worker build is the repository's no-build script

The private corpus, selection provenance, independent annotations and per-case result report remain outside all Git roots. Nothing from it is uploaded to this repository. Synthetic fixtures are separately labelled and do not contribute to the 100-message count.

## Limits that remain explicit

- Live model accuracy, live IMAP authentication and live PostgreSQL/API behavior were not measured by the local corpus run. Classifiers/import/log/database effects were doubles and network was denied
- Six routing-uncertain completed notices are retained rather than mapped by inference; one blocks later UIDs until a supported fix or operator decision
- API idempotency is by user/provider/Message-ID; a strong same-body BCI duplicate candidate with distinct identities remains uncertain. Identical-body suppression could also erase a genuine repeated purchase, so it was not invented. No historical entries are reimported or removed
- Independent header-only evidence identifies a separate BCI transfer sender as a possible coverage gap. The allowlist was not broadened without full authentication/layout/routing evidence
- TLS validation opt-out exists in pre-existing configuration; no production security setting was changed and its value was not read as part of credential-free audit
- Root Next application code/API schema was inspected for identity compatibility but not changed; this is a focused worker validation, not a full root-app end-to-end run

## Review and rollout gate

Before merging/deploying: independently review the exact candidate SHA, final tests, unchanged production cursor/identity contract and rollback plan. Verify `master` has not advanced; preserve unrelated changes. A draft branch/PR does not itself trigger the cron's production branch.

After an authorized merge: confirm the exact remote merge SHA and Railway deployment commit. Observe a natural `*/10` cron run, not a manual import, and inspect bounded logs for status, cursor advancement only after confirmed disposition, cleanup, authentication and failures. Do not claim completion merely because a build starts.

Rollback: restore the worker code to the reviewed previous version while preserving the existing PostgreSQL cursor, processing logs and import identities. Do not reset UID/UIDVALIDITY, replay history or manually mutate financial movements. If the new release blocks, keep the cursor and report its fixed reason before deciding on a code-only rollback.

### Lock and cleanup references

The advisory ownership check uses PostgreSQL's documented bigint key encoding in [pg_locks](https://www.postgresql.org/docs/17/view-pg-locks.html). Driver behavior was inspected against installed postgres.js 3.4.9 and node-imap 0.8.19. A virtual PostgreSQL wire (no TCP, no real credentials) reproduces a blackholed existing-query response and verifies client timeout plus physical-wire destruction. IMAP failure cleanup destroys the underlying socket rather than relying on queued LOGOUT/socket.end.
